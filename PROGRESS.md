New `ACCEL_TICKS_BASE` (2), `ACCEL_TICKS_PER_TILE` (16), `BRAKE_FACTOR` (2), `CORNER_MIN_SPEED` (0.25). `FLY_LOITER_RADIUS` 3 to 6 tiles: flyers at double speed crossed the old radius in so few ticks that they no longer circled before landing (`flight.test.ts`).
- **Engine** (`systems.ts` `movementSystem`/`throttle`/`accelOf`, `simulation.ts` side tables `speedNow`, `headX`, `headY`): a moving unit has a current speed that gains `top / (2 + 16 x hull radius in tiles)` per tick (at least 1), so a micro hull takes about 5 ticks to reach top speed, a light 7, a heavy 9, a super-heavy 13 and a colossus 18. Braking is twice as fast. Cornering: the cap is top speed x the cosine of the angle between the direction of travel and the next leg (floor 25%), and it looks one waypoint ahead and starts braking at the braking distance so the unit takes the next corner at the right speed. Flyers use the acceleration only (their arcs already limit turning). The stuck check now measures progress against the distance actually moved rather than top speed. Allocation-free: three number tables, a few square roots per moving unit per tick. Perf budgets pass; cost not measured separately.

Both are validated (unit list cap 200, identifier name, integer value within 2^30) and go through the existing socket rate limit. ## 2026-10-29 (harvesters stay near depots; list chains in the script language)

- **Why:** harvesters wandered off to far fields, crowded one depot and could end up with nothing to do. The old block picked a random one of the 4 fields nearest the *unit*, with no idea of depots or other harvesters.
- **Language:** a list is the result of a find call and lives only inside a chain: `findDepots().filter(d => ...).minBy(d => dist(d))`. New IR expression `chain` (`ir.ts`), steps and their rules in `flow/lists.ts`, checked in `check.ts` (one find call first, list steps, one ending step that gives a number, at most 8 steps, no nested chains, functions are one expression; function parameters count as locals for memory), compiled in `compile.ts` to inline loops over a shared 32-entry buffer (new VM ops `ListSrc`, `LBegin`, `LNext`, `LKeep`, `LPut`, `LKey`, `LEnd`, `LStep`, `LSort`, `LTake`, `LArg`, `LTerm` in `run.ts`), parsed and printed in `text.ts` (`exprText` is now exported; `.random()` uses `rand()`). Costs: 2 per entry per function step plus the body, sort +1 per entry, lists capped at `LIST_MAX` 32, so the worst chain stays far inside `HANDLER_LIMIT` (test: a full 32-entry filter, map, sort, minBy chain is under 2000 cycles). `const x = <any expression>` is now allowed in text and becomes a call to the new query `calc(x)` (printed back as a plain const). I first called it `value`, which broke programs that already use a variable or parameter called `value`; `calc` is unused in the repo.
- **Game calls** (`api.ts`, new API group Lists): `findResources(min)`, `findResourcesNear(h, min)`, `findDepots()` (includes the caller, so a depot sees itself), `findChargers()`, `findSites()`, `findDamaged()`, `findEnemies()`, `findAllies()` (the last two use the sensor and its energy); plus `distBetween(a, b)`, `crowd(h, r)` and `crowdOver(h, r, limit)` (own harvesters near a thing, from the spatial grid, r capped at 20). The find calls scan the unit or resource list once, like `nearestDepot()` and `randomResource()` already do (O(units) per call, cost 8 to 16 cycles); they keep the nearest 32 by insertion into a sorted prefix with no allocation (`randomResource` allocates and sorts every call; it is unchanged and still there).
- **Harvesters** (`blocks.ts`): `HarvestLoop` and `DispatchHarvesters` now choose a home depot (nearest, but each harvester beyond `crowdLimit` within `crowdRadius` tiles adds 12 tiles) and then a field among the `fieldsToChooseFrom` nearest that depot, each harvester within 3 tiles of a field adding 6 tiles. New settings `crowdLimit` (4) and `crowdRadius` (6); `fieldsToChooseFrom` and `minMatter` keep working, so saved programs still compile. `HarvestLoop` also handles `lost` and `blocked` (a field it cannot reach is left out of the next choice), and a free harvester with cargo now only docks where there is room (before, it kept re-docking at a full silo). Starter classes still fit their memory (Harvester 11 of 16 slots, Resource Silo 7).

The one stuck state I found in a 3000-tick default match is correct but looks like a bug: two harvesters wait with a full load once the base's silos are full (the player needs another silo). The test does not count them as stuck. If harvesters still get lost in play, `TODO.md` asks for a repro (map, tick, which unit).
- **Tests:** `lists.test.ts` (every step, empty lists, stability, cap, cost bound, text round trip, every checker message), `harvest-ai.test.ts` (nearest-depot field, near beats big and far, overcrowded depot passes to another, deterministic, no harvester idle for 150 ticks over 3000), a graph test and the docs test. Three existing tests changed for the new behaviour: `flow.test.ts` (`const ask = 1;` is now valid, so the old "must be bound to a call" messages are gone, and its tiny host gained `calc`), `sim.test.ts` (the silo test no longer expects a random pick among 4 fields; it removes the starting harvesters so crowding does not apply), `graph.test.ts` (expanded text). `npm run typecheck` passes. `npm test`: everything passes except the `perf-scaling` 64 and 128 unit fights, which failed once on the full run and passed in two re-runs (the known load flake).
