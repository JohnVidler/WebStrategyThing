# Server

[← Back to the README](../README.md)

The server is authoritative: it runs every match loop and every unit script. See [deployment.md](deployment.md) for running it.

- The **server is authoritative** and runs all scripts, so opponents never receive your code and clients can't cheat by editing it.
- Each tick the server encodes a binary delta (despawns, component removals, changed networked fields, transient events); entity ids and counts are varints, and positions travel as u16 at 1/64-tile precision (`wireShift` on the component). A joining client gets a full snapshot first.
- **Rooms:** each room is its own `Match`, created on first use and closed a minute after it empties. A client picks one with `?room=name&map=map-id`; opening the page without a room shows the **lobby**, with open rooms and a new-game form offering five maps with terrain previews. The room list is served at `GET /api/v1/rooms`; WebSockets use `/api/v1/ws`. The maps are Crossroads (64×64), Small Basin (48×48), Broken Country (72×72), Twin Ridges (80×56) and Highlands (96×80). Up to 20 rooms exist at once. **Waiting room:** a free-for-all or co-op room starts in a lobby phase: players who join get no base yet and time stands still. The server broadcasts a `lobby` message (players, host = lowest id present, `minPlayers`) whenever it changes, and the host's `startGame` (needs 2 players for a free-for-all, 1 for co-op) sets every base up at once and sends `started`. Leaving the lobby frees the seat immediately (no reconnect grace) and hosting passes on. Single-player rooms skip the lobby, and a match already under way still takes a late joiner into a free corner. **Resign / defeat / spectating:** the **Resign** button (press twice) sends `forfeit`, which marks the player defeated at once (so closing the tab afterwards starts no reconnect wait) and destroys their forces on the next tick (in co-op their bot is left alone); a player with none left while the match goes on (forfeited or destroyed; destruction is noticed when the scoreboard is reported, every 5 ticks) gets a `defeated` message and the client offers **Spectate** or **Leave to menu**. `spectate` (allowed only for the defeated, or anyone once the match is over) re-sends `welcome` with `spectating: true` and `fog: false` plus a full snapshot, and from then on the player gets the unfiltered per-tick delta; their orders are ignored. The `leave` message leaves for good at any time (`resigned`; the legacy `resign` forfeits if it can and otherwise leaves), and a defeated player who just disconnects isn't waited for. Which messages a client may send before the start or while spectating is one shared rule, `messageAllowed` in `net/protocol.ts`; a `loadDesigns` sent then is answered with a `designsLoaded` carrying an error, so the client's design store recovers. **Reconnecting:** each tab sends a per-tab token (`sessionStorage`); if the connection drops the client retries with backoff, and the server keeps the player's base for 60 seconds and, on reconnect, resends the welcome, a full snapshot, class programs and task queues. Players without a token are removed immediately. **Pausing:** a match only runs with at least two connected players and nobody missing; otherwise the server stops stepping the simulation (orders and base set-up still apply) and clients show a "Game paused" overlay listing the reasons (waiting for another player, or a named player disconnected). The reconnect grace period is measured in wall-clock time, so a paused game can't wait forever. The game clock only counts unpaused time, and the lobby shows it per room, along with each player's score and whether they are away or out, so it's clear which games are already well under way.
- **Fog of war** (`game/vision.ts`, `Interest` in `net/codec.ts`): each client's delta is filtered to its own entities, resource fields and anything within its vision. Entities entering view are sent in full and entities leaving view are despawned on the client, so hidden positions, health and module switches never leave the server. With `FOG=off`, one shared buffer goes to everyone.
- **Developer commands** (`net/dev.ts`, `game/dev.ts`, `Match.dev`): the dev-build Dev Options menu spawns and removes things on any team, toggles fog, pauses and ends the match. The server obeys them only when started with `WST_DEV_TOOLS=1` and never when `NODE_ENV=production` (`npm run dev` sets the first; the Docker server image sets the second and never the first, so it refuses every one), and the client menu is compiled in only when the client is built with `WST_DEV_TOOLS=1` (the Docker client build never is, and fails if dev code reaches the bundle). Every command is validated and bounded like any other message.
- **Limits** (`server/src/server.ts`, `match.ts`, `engine/src/game/rules.ts`): a request target that is not a plain path (`//`, `*`) gets 400 (HTTP) or a close (WebSocket), and no error on a socket or in a message handler can end the process. A tick that throws ends only its own match. A game socket may send 200 messages in a burst and 100 a second after that, and 4 MB in a burst and 1 MB a second (a frame is at most 1 MB); a client over either is closed with 1008. One player may have 500 messages waiting for the next tick. At most 2000 menu sockets, 30 sockets and 5 open rooms per client address (`WST_MAX_SOCKETS_PER_ADDRESS` and `WST_MAX_ROOMS_PER_ADDRESS` change them, `0` turns one off; the address is `X-Real-IP`, trusted only from a private address, and the client Nginx sets it from `X-Forwarded-For`, see [deployment.md](deployment.md)), and 20 rooms in all. A player may make at most 256 classes in a match (`MAX_CLASSES_EVER_PER_PLAYER`), retired ones included, on top of 48 active. Path planning has a deterministic work budget per tick (`PLAN_WORK_PER_TICK`): units given a route beyond it head straight for the goal until their turn.
- All client input is queued and applied at tick boundaries. With a seeded RNG, integer positions and deterministic iteration order, **seed + command log reproduces a match exactly**: the basis for replays (and verified by a test).

## Background music

The server lists tracks at `GET /api/v1/music` and streams them (with Range support) from `GET /api/v1/music/<file>`. Tracks and `music_manifest.json` live in `./music` in the project root, or `MUSIC_DIR`. See [deployment.md](deployment.md) for the manifest format and the Docker mount.

## Sound effects

The server lists the sound manifest at `GET /api/v1/sound` (`{ sounds, tags }`, with files that are missing and malformed entries dropped) and serves each file from `GET /api/v1/sound/<file>`. Unlike music, the sound folder ships in the repository and the Docker image: files and `sound_manifest.json` live in `./sound`, or `SOUND_DIR`. Only files named in the manifest are served. See [SOUND_EVENTS.md](../SOUND_EVENTS.md) for the tags and the manifest format.

Campaigns (single-player levels, see `campaigns/README.md`) are part of the repository and are copied into the server image, unlike music and sound. The server lists them at `GET /api/v1/campaigns`; `CAMPAIGNS_DIR` overrides the folder (default `./campaigns`).
