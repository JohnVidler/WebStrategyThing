# Game design and engine

[← Back to the README](../README.md)

How the simulation works: classes, programs, energy, construction and combat. Server-side match handling is in [server.md](server.md); the browser side is in [client.md](client.md).

## Flyweight: classes vs. units
- **Intrinsic (shared, per class):** a `Blueprint` holds the part ids, derived `BlueprintStats`, and the compiled `Program`. The part catalogue is code, so it is never transmitted. A blueprint goes over the wire once, as `{id, owner, name, parts}`, and clients re-derive stats from the shared catalogue.
- **Extrinsic (per unit):** a few typed-array fields (`Position`, `Unit{blueprint, owner}`, `Health`, …) plus a `VmState` (pc, stack, memory) that stays on the server.
- Uploading a new program swaps one reference on the blueprint, and every unit of that class reboots into it on the next tick.

## ECS
- `defineComponent(name, schema, {networked})` declares numeric fields. Each store keeps one typed array per field, indexed by entity.
- Systems write the arrays directly and call `store.markChanged(e)`. Only components marked `networked` are tracked and replicated; intents and cooldowns stay on the server.
- `EntityHandle` (generation + index) is what scripts hold, so a handle to a dead unit resolves to `-1` and never to whatever reused its slot.
- `GAME_COMPONENTS` order is the wire id. Only append to it.

## Compute as a resource
- Every instruction costs 1 cycle, and builtins add their own `cost` (sensing is expensive). A unit gets `cyclesPerTick` from its CPU parts.
- A program that runs out of budget **pauses and resumes next tick**, so a weak CPU runs the same code but reacts more slowly. An expensive call can overspend, and the unit pays the debt back over later ticks.
- Memory parts set how many variables a program may declare. A program that needs more is rejected for that class.
- Faults (division by zero, stack overflow) cost the unit one tick to reboot, and the client shows them as a red tint.

## Orders, task queues and scripts
- Every unit and building has a fixed-size `TaskQueue` (`game/tasks.ts`) of high-level tasks: `MOVE`, `ATTACK`, `HARVEST`, `DOCK`, `STOP`, `CHARGE`, `BUILD` and `SUPPLY`, each with x/y, a target handle and flags.
- **Right-click** is resolved on the server (`Simulation.issueOrder`) into the context task for each selected unit: an enemy means `ATTACK` (if it can fight), a resource means `HARVEST` (if it has a cargo bay), your own construction site means `BUILD` (if it has a build arm), your own depot means `DOCK`, your own charging pad means `CHARGE`, your own unit below 25% energy means `SUPPLY`, otherwise `MOVE`. With a building selected, a right-click queues a `MOVE` on the building, which its script treats as the rally point.
- Player tasks are always **appended** and flagged `FROM_PLAYER`. Unless the player holds Ctrl (or Shift, in browsers other than Firefox, which always opens its own menu on Shift + right click) they are also flagged `URGENT`. The script decides what that means: the starter classes drop their plan for an URGENT order, but a class could ignore it, finish its current job first, or refuse orders while in combat. Scripts read and edit their queue with `taskCount/taskType/taskX/taskY/taskTarget/taskFlags/taskDrop/taskFirst`, and acknowledge an order with `taskAck` so its URGENT flag isn't mistaken for a new order later.
- Each owner (and only the owner) is sent the full queues of their units whenever they change. The client routes a path through every queued task with the same A* the server uses, so no path data crosses the wire.

## Action buttons
- The side panel's action grid has the **common actions** (`game/actions.ts`: move, attack, stop, harvest, unload, recharge) plus Demolish. Each is enabled when at least one selected unit has the modules for it, and the server re-checks per unit (`Simulation.issueCommand`), so a mixed selection only commands the units that can comply.
- A class declares its own buttons with `Button` event blocks: `on(Button, { label: 'Overdrive', key: 'O' }, () => { ... })` (add `aim: true` for buttons that take a map target). The block *is* the button and its code runs when it is pressed: the server raises that one handler (`Simulation.issueButton`) with the picked tile and target, with no task involved. The client compiles the owner's program sources itself to learn the buttons, so program sources are only ever sent to their owner.
- Common actions (move, attack, ...) are still only tasks: the program decides what they do, and an `Order` block can react the moment one arrives.

## Buildings talk to units only while they visit
- A unit **visits** a building when it is produced there or docks there (`dock()`). Each visit raises a `Visitor` event (reason `PRODUCED` or `DOCKED`, and the visitor's handle) on the building. While that handler runs the building can inspect the visitor (`visitorCaps()`, `visitorLastHarvest()`) and give it tasks with `order(type, x, y, target)`.
- The link lasts until the handler finishes. `order()` only ever targets the current visitor, so storing a unit's handle gives a building no lasting control over it.
- The harvest loop is built from this: the HQ sends a new harvester to a field, the harvester's script gathers until full and docks, and docking hands it back to the HQ's script for the next job. A factory script can also queue units itself with `unitClassCount()`, `queueUnit(i)` and `queueLength()`.

## Terrain and movement
- `Terrain` (`game/terrain.ts`) is a height map generated in one quadrant and mirrored, so every corner is equally fair: 0 is open ground (`passable`), rock is 1..9, its depth inside the outcrop (the rim is 1). Every fourth outcrop, and the Bastion wall, is a **cliff**: at least 3 high right from its edge. Building footprints block cells too. The wire form is one height digit per cell.
- **Liquids** (2026-10-30): below ground level a cell holds liquid, `Terrain.depth` 1..9 (`MAX_LIQUID_DEPTH`): 1-2 shallow water, 3-5 deep water, 6-8 lava, 9 a void (`liquidKind`). A cell is rock or liquid, never both; `passable` stays 1 only on dry open ground, so code that knows nothing of liquids treats them as rock, and `heightAt` reads 0 over them (`depthAt`, `isRock`, `elevationAt` tell them apart). Vision treats only rock and buildings as opaque; shells fly over liquid. The wire form is one character per cell: `0` ground, `1`-`9` rock, `a`-`i` depth 1-9; `Terrain.shape` counts `setElevation` calls (a cache key that ignores buildings). The generator adds water lakes, lava pools, chasms and winding rivers with dry bridge strips (`LiquidSpec` on a `MapDefinition`) after every other random draw, so maps without a spec are unchanged. Bodies are mirrored like rock unless the spec says `free`, which scatters them over the whole map (rivers are never mirrored); connectivity is checked from the first base, not the map centre (which may be a river), over what wheels can enter (dry ground and shallow water), carving a 3-wide dry corridor only where a base is cut off; depth is set last from the distance to the shore (`settleLiquids`).
- **Wading**: `Mobility.wade` is the deepest depth a unit may enter (`DEFAULT_WADE` 2 for every ground drive, `motor.amphibious` 5, `motor.hover` 8), `Mobility.hover` skims at full speed. `Terrain.enterable/fits` take both, the room cache is keyed by climb and wade, and buildings, aircraft landing and spawning use the dry-only `DRY` mobility. Wading is slower (`WADE_SPEED_PERMILLE`: 60% shallow, 45% deep or lava; a hover unit loses nothing) and costs more in the path search (`WADE_STEP_COST`, tenths of a dry step), while the heuristic stays at the dry cost so it is still a lower bound. String-pulling may not take a shortcut that wades more of the line than the cells it replaces (`lineWalkable(..., maxWet)`). Maps without liquid skip all of this (`Terrain.hasLiquid`). `liquidSystem` runs every `LAVA_HEAT_TICKS` ticks: a hover unit over lava takes `LAVA_HEAT_DAMAGE`, a ground unit left in lava `LAVA_STRAND_DAMAGE`, one over a void is destroyed. Legs cannot be mixed with the new drives (the existing legs rule), so a unit never both climbs and wades.
- **Mobility** (`Mobility`, from the blueprint stats): `climb` is the highest rock a unit may stand on (0 wheels and tracks, 1 light legs, 2 heavy legs, 9 colossus legs; legs move at half speed on rock), `clearance` the cells it needs clear around its centre (1 for super-heavy and colossus hulls, so they need a 3-wide way). `Terrain.fits` answers both, with a per-climb distance map cached on `Terrain.version`.
- Ground units follow A* paths (`game/path.ts`: 8-way, no corner cutting, string-pulled, by mobility; a big hull that starts in a tight spot may squeeze out). Flying units (rotor) go straight and only land on passable, free cells.
- **Size tiers** (`PartDef.size`): 0 micro, 1 light, 2 medium, 3 heavy, 4 super-heavy, 5 colossus. A unit is produced only by a building with a factory module of exactly its tier (`factory.micro` ... `factory.colossal`, `PartDef.factoryTier`; `BlueprintStats.factoryTiers` is the bit mask, `factoryCanBuild` the test). Titan Works has the super-heavy and colossal modules; the old `factory.basic` id is an alias of the light module. The chassis `radius` sets the drawing, separation (radii plus a small gap) and, beyond half a tile, how close weapons and docks must get (to the hull). Heavy modules have a `minSize`.
- Units push apart each tick (ground and air separately), never onto ground they could not walk on. Crowded arrivals count as "arrived", and jammed units re-plan.

## Energy, modules and power
- Every unit and building stores energy (chassis buffer + batteries). Modules use energy when used: the CPU per 100 cycles actually run (a CPU with nothing to do uses nothing), motors per tick moving, sensors per scan, weapons per shot, cargo bays per tick harvesting, build arms per tick building, factories per tick producing. Without energy the action doesn't happen.
- Energy moves by **transfer** (`Simulation.transferEnergy`), with one rule: the giver must hold at least the amount offered, and reach depends on the giver's scale (units 1 tile; buildings 3 tiles from their edge). **Charging pads** are buildings that transfer to nearby own units automatically every tick; scripts use `giveEnergy()`. The starter scripts push a `CHARGE` task below 25%, and a `SUPPLY` order sends a healthy unit to revive a flat one.
- Buildings link into **power networks** (`game/power.ts`) when their edges are within reach: 1 tile by default, more with energy antenna modules (3/6/12). Only the shortest links that keep a network connected are kept (a minimum spanning forest), so links re-route when a building is lost; links up to 1 tile are uncapped, but a longer antenna link carries at most `ANTENNA_THROUGHPUT_PER_TILE` (`rules.ts`) per tick per antenna times the host building's footprint, shared by everything crossing it, in total over both directions (`routeEnergy` in `power.ts`; the clusters, bridges and routes are built once per rebuild by `powerTopology`; because the links are a spanning forest the bridges form a tree, and a cluster is served its proportional share first, then takes any energy still idle from its own cluster and the nearest others); unfinished construction sites hang off one finished building and never bridge others. Each tick, solar (day/night cycle) and wind (drifting) generation (deliberately small: `SOLAR_PANEL_OUTPUT`, `WIND_TURBINE_OUTPUT` in `game/parts.ts`) goes first to normal buildings, then to storage in `CHARGE_STORE` mode. Storage in `DISCHARGE` mode covers shortfalls (at most 2% of its capacity per tick, `STORAGE_DISCHARGE_FRACTION`). Storage buildings choose their mode in script. Each owner is sent their networks' totals (`networks` message), shown in the info bar and header, with the selected building's network highlighted. The report also gives the energy each building took from or gave to its network. The client routes that back to the sources to find the load on each link, and the dots moving along a link go faster the more energy it carries.
- **Weather** (`Weather`, `skyKind`, `strikeAt` in `game/power.ts`; constants in `rules.ts`): the match is cut into `SKY_SLOT_TICKS` slots, each dry or one `Sky` (rain, storm, heatwave, dust, mist) from a hash of the seed and slot, so client and server agree with no extra traffic and nothing draws from the `Rng`. `Weather.mix` holds the percent of each kind now; the first `skyRampTicks` of a slot (between `SKY_RAMP_MIN_TICKS` and `SKY_RAMP_MAX_TICKS`, picked per slot, so most changes creep and some are quicker) slide linearly from the previous slot's kind, and the dev tools can force a kind and scale the intensity. Effects are weighted sums of a per-kind table: `Simulation.solarNow()` (sun scaled by the gain, held to the cap; above 100 in a heatwave) for panels on buildings and units, `windNow()` (lifted to the floor, held to the ceiling), and `hazeNow()`, which shrinks every viewer's sight (`visionAt`). `sunNow()` (light, night sight) is untouched, and the dev tools' fixed sun and wind levels override the weather. In a storm `lightningSystem` stuns (`LIGHTNING_STUN_TICKS`) everything within `LIGHTNING_RADIUS` of each strike; the strike times and ground spots are pure functions of the tick (`strikeAt`, `strikeSpot`), and a strike that picks out a unit sends `SimEvent.Lightning`. The client (`precipitation.ts`) draws everything from the mix, none of it affecting the simulation.
- **Steam vents** are fixed map features (`game/features.ts`, component `Feature`, networked once like the map's resource fields). A building whose footprint covers a vent gets `steam turbine` output: `BlueprintStats.steam` (peak, summed) and `steamTurbines`; `Simulation.ventsUnder[e]` (recounted whenever the networks are rebuilt) says how many vents lie under it, and `powerSystem` yields `steam * min(vents, turbines) / turbines * STEAM_GENERATION_MULTIPLIER` per tick whatever the hour or wind. Vents never block anything. They come in mirrored fours (one per quadrant) so no start has more than another, and placement draws from its own `Rng` (`seed ^ 0x7e57fea7`), so it does not change the numbers other map setup draws.
- **Scenery** (shack, tank, hall, ruin) is the same component with a solid kind: it blocks movement and sight through `Terrain.occupy` (server at spawn, client in `refreshStructures`), cannot be selected or damaged, and costs no tick time. It comes in clusters with 4 open tiles all round so no lane is cut off. Hand-made campaign terrain gets neither.
- Modules can be switched on/off per unit (`setModule()` from scripts, or from the side panel). Stats for each on/off mask are derived once and shared by every unit with that mask (`statsFor`), so the flyweight survives per-unit switches.

## Resources, production and construction
- Resources are physical: they live in buildings with **silo** modules, and a player's **common pool** is the total across all their silos. Silos fill up, and a destroyed silo loses its contents. `dock()` fills a depot (as much as fits); `take()` loads from one back into a cargo bay.
- A class costs `10 × mass + cycles`, multiplied by 2.5 for each size tier above medium (units only; production energy too), and its build time scales with mass. Buildings with a `factory` part have a production queue; the cost is paid from the pool when an item is queued.
- New buildings are placed from the **build bar** as construction sites. Builders (units with a `build.arm` module) invest resources each tick: from their own cargo first, then from the common pool, but only if the site is linked by the power grid to a silo. Remote sites need resources carried to them (the starter Builder script hauls them automatically) or a chain of pylons. Buildings with a `build.crane` (the starter Construction Tower) build sites within 4 tiles.
- **Demolish** (X, pressed twice) cancels a site with a full refund, or knocks down a building for half its cost. Classes can be **retired** in the designer so they can no longer be produced or placed.
- Building frames (1×1, 2×2, 3×3 with 8/16/31 slots) are immobile and are the only frames that can carry factory, silo, charger, generator, battery-bank and antenna modules.
- **Building costs energy** as well as matter: `footprint² × 50`, in proportion to the matter invested (`game/rules.ts`). A site linked to a silo's network draws it from that network; otherwise the builder pays, and stops at 25% of its capacity so it can retreat to a charger (the default Builder script goes at 30%). Idle default builders pick up the nearest unfinished site.
- **Decay:** a unit with no energy for 60 seconds (`DECAY_TICKS`) breaks down into a matter block worth its cost. Charging or supplying it first resets the countdown.

## Weapons
- Each weapon kind pays differently (`game/parts.ts`): the **light gun** is free, the **cannon** uses matter (from the cargo bay on a vehicle, from the silos on a building), and the **laser** uses a lot of energy per shot (its damage scales with the energy spent, which a script can set with `laserPower(energy)`; 8 damage at the full 20). The **tesla coil** stuns the CPU of every unit and building around it, friend or foe, then recharges slowly; on a vehicle it stuns the vehicle too, for half as long. Tesla range, stun length and cooldown are constants in `game/rules.ts`.
- **Missile launchers** (small, medium, large; `game/missile.ts`) do not hit instantly: each shot spends matter (like the cannon) and spawns a missile, an entity of its own with a `Missile` component, `Position` and `Health`. Its warhead does `matter × MISSILE_DAMAGE_PER_MATTER` damage (12 per matter: 48 / 144 / 360), so damage is proportional to what the missile costs. It homes on the target at a limited turn rate (7 / 4.5 / 2.5 degrees per tick), so it flies wide arcs and can be outrun, and a fresh missile leaves up to `MISSILE_LAUNCH_SPREAD` off the line to the target so the arc shows. Bigger missiles are slower (5 / 3.5 / 2.2 tiles per second), last longer and burst bigger (blast 1 / 1.5 / 2.2 tiles, damage falling to `MISSILE_EDGE_DAMAGE` at the edge). It bursts when within `MISSILE_FUSE_RADIUS` of an enemy, when its flight time (40 / 60 / 90 ticks) runs out, or at the map edge; the burst hurts enemies only. If the target dies it flies straight on. Tuning lives in `PART_TUNING` (`MissileTuning`).
- Any hit-scan weapon (gun, cannon, laser) can shoot a missile down: it has hit points (4 / 20 / 60) and a `Detected` sweep for `ENEMY` reports it like any enemy. A shot at a missile only connects with its `hitChance` (30% / 60% / 100%), so small missiles are hard to hit and big ones are big, slow targets. A missile that is shot down does not burst. Your own missiles are always visible to you; other players' only inside vision. You can order units to shoot one down yourself: right-click an enemy missile (or Attack, then click it). The **flak cannon** (`flak.cannon`) is the dedicated answer: an air-burst that hits every enemy missile within 1.5 tiles of its target for 12 damage, with no chance to miss, and does nothing to units or buildings; a `Detected` block can watch for `MISSILE` alone. Starters: Flak Truck (mobile) and Flak Turret (building).
- **Module damage** (`Simulation.damage` / `hitModule`, `game/rules.ts`): every hit also lands on one module of the victim, for the same damage as the hull takes. A weapon's `aim` (set by a program with `config.aim(M_WEAPON)`, `M_MOTOR`, `M_CPU`, ... or `M_ANY`) picks the class of module; `M_ANY`, the default, rolls a random part each hit (every part but the chassis is as likely as any other, so armour, memory and batteries soak up hits that land on them), and an aimed hit with no working module of that class falls back to a random one. A module breaks once it has taken its `integrity` in damage (`MODULE_HP_BASE` + `MODULE_HP_PER_MASS` × mass unless the part sets its own; **legs are fragile**: 12 / 30 / 100). A broken module is excluded from the unit's stats exactly like a switched-off one (a unit on broken legs has no speed, a broken gun no weapon, a broken CPU no program) but cannot be switched back on; the bit is in `Modules.broken` and clients derive stats from `off | broken`. The roll is a hash of the tick, the victim and a counter, so it never touches the match's random stream. Repair modules mend module damage first, broken modules before merely worn ones, then the hull, at the usual matter cost per point; a hit always costs the hull at least as much as the module, so a unit with a broken module is always short of hit points. Programs can read it with `moduleBroken(i)` and `brokenOf(h)`.
- **Flamethrower** (`flame.projector`, kind `flame`; `game/flame.ts`, constants `FLAME_*` in `game/rules.ts`): each shot lobs a fireball (about every other tick; matter is paid 1 per `FLAME_SHOTS_PER_MATTER` shots), an entity with Position and a `Flame` component (`state` 0 in the air, `arc` the progress of the lob; `Simulation.flameFlights` holds the rest). It flies at `FLAME_SPEED` over everything to the target's spot, lands, and the same entity becomes a fire (`state` 1, `life` in 32 steps) for `FLAME_BURN_TICKS`. Every `FLAME_BURN_INTERVAL` ticks a fire does `FLAME_BURN_DAMAGE` to every grounded unit and building it touches, owned by anyone. An enemy shield across a fireball's hop turns it back (the battery pays `FLAME_SHIELD_DAMAGE`) for at most `FLAME_MAX_DEFLECTIONS` hops. A carrier takes `FLAME_VULNERABILITY` times damage (`Simulation.damage`), and `deathSystem` makes it throw `FLAME_BURST_COUNT` fireballs (more for a building) at random distances up to `FLAME_BURST_REACH` tiles all round, so units packed within about 2 tiles of each other set each other off in a chain; the starter **Flamer** costs about 1.5x a Tank (the projector is mass 14) and its program (`EngageEnemies` with `spareAllies`) holds fire while one of its own stands within 3 tiles of the target (`flameBurst`, drawn from the match's `Rng`). Rain puts fires out: each tick a fire's burn time falls by `1 + wetness * (FLAME_RAIN_BURN_FACTOR - 1) / 100`, where `Weather.wetness` is the rain plus storm percent. At most `MAX_FLAMES` fireballs and fires exist at once; the extra are simply not made.
- Buildings can carry weapons (the starter **Laser Turret**); a building's weapon is activated when construction finishes.
- **One starter unit per weapon**, to play-test each: Scout and Hawk (light gun), **Tank** (cannon, one cargo bay), **Lancer** (laser, two battery cells), **Stormer** (tesla coil: only stuns, so it needs friends) and **Rocket Truck** (medium missiles, two cargo bays, long sensor). They all run the fighter program; Tank and Rocket Truck add a resupply handler that walks to the nearest stocked silo when the cargo bay runs low, then carries on. The HQ and Resource Silo no longer send a unit with a weapon harvesting.

## Energy shields
- The **shield emitter** (`shield.emitter`, slot `shield`, `game/shield.ts`) casts an arc: centred on the owner, `range` out from its centre, `arc` wide, pointing along `head`. It has no entity of its own: `Simulation.shields` holds the settings, and the networked `Shield` component (heading and arc in 256ths of a turn, range in tenths of a tile, `active`) carries them to clients. One emitter per class. `Simulation.shieldList` is rebuilt each tick by `shieldSystem` (before weapons fire) and lists the shields that are up; every other system only checks its length, so a match without shields pays almost nothing.
- **Cost:** `use` (5) energy per tick at the starting 120 degrees and 3 tiles, scaled by arc and range together (240 degrees at 3 tiles costs 10). It is billed with `Simulation.spend`, so a unit uses its battery and a building its store (refilled by the grid). If a tick's cost cannot be paid the shield is down for that tick, with no collapse. A switched-off or broken module, or an unfinished building, has no shield.
- **Easing and interference:** arc, radius and heading do not jump: each tick they move `SHIELD_EASE` (20%) of the way to what a script asked for (`wantArc`, `wantRange`, `want`), the heading also capped at `SHIELD_TURN_PER_TICK`. Wherever the arcs of two shields cross (any owners; `circleArcCrossings`, found through the spatial grid) both pay `SHIELD_INTERFERENCE_DRAIN` (1.5x) per crossing point, so two facing shields that cross twice pay 2.25x; the count is replicated as `Shield.strain`.
- **What it stops** (enemies only: not allied by owner or team): a segment from one position to the next is tested against each live shield's arc (`arcCrossing`, `shieldBlock`). Cannon shells and missiles are tested each step (a missile's whole warhead is taken, so no blast beyond the arc), hit-scan weapons (gun, cannon at a missile excepted, laser) from shooter to target, and walking or flying units for every move: a unit stops short and keeps its path. Tesla and flak are not affected. Pathfinding does not plan round a shield (it is a dynamic wall), so a unit that wants to cross simply waits at it; armed ones shoot the owner and wear it down.
- **Damage:** `shieldAbsorb` charges `SHIELD_ENERGY_PER_DAMAGE` (4) energy per point of damage to the owner's store. If the store cannot pay, `collapse` empties it, breaks the emitter module (it stays out until repaired) and hurts the owner for `SHIELD_BURST_DAMAGE_FRACTION` (3%) of its energy capacity, crediting the shooter. Events: `ShieldHit` (owner, direction and damage packed in `b`) and `ShieldBurst`.
- **Aim is a script's job**: the engine never chooses where a shield points, it only turns the arc (at most `SHIELD_TURN_PER_TICK`, 0.15 rad a tick) towards the angle a program set with `config.shieldAngle(degrees)` (0 east, 90 south). The built-in **`ShieldGuard`** block (`flow/blocks.ts`, every 3 ticks) points it at `incomingBearing()` (the nearest enemy shell or missile in flight within 10 tiles, no sensor needed), else at `bearing(scan())` (the nearest enemy the sensor finds), else leaves it. `config.shieldArc(degrees)` and `config.shieldRange(tiles)` set the size within the emitter's limits (240 degrees, 6 tiles; never inside the hull). Queries: `shieldUp()`, `bearing(h)`, `incomingBearing()`.
- Starter content, both running `ShieldGuard`: **Shield Tower** (small frame, basic CPU, long sensor, two battery banks) and **Aegis** (medium chassis escort, no weapon, basic orders).

## Saved designs
- A design file (`game/designs.ts`) is plain JSON: `{format, version, build, savedAt, classes: [{name, parts, program, retired, base}]}`. `build` fingerprints the default class set, and `base` is the hash of the default a class was saved against. Together they separate "the player edited this default" from "the default changed upstream since".
- The client autosaves the player's classes to `localStorage` and restores them on join; downloads and uploads use the same format. The server applies a whole set with one `loadDesigns` message (`Simulation.loadDesigns`). Classes are matched by name: same parts means the program is updated in place; different parts means a new class, with the old one retired. Units already built keep their class.

## Radar
- The `radar.pulse` module (slot `radar`, `M_RADAR`, capability `HAS_RADAR`) is a one-shot scan, not a continuous one. A program calls `radarPulse(energy)`: it spends that energy (capped by the module's `radarMaxEnergy`), range is `RADAR_ENERGY_PER_TILE` energy per tile, and the module rests `RADAR_COOLDOWN_TICKS` afterwards (`radarCooldown()`). It returns the contact count, or -1 on failure.
- Contacts (every non-allied unit and building in range) are not entities: `Simulation.radarPulse` records a `RadarPulse`, the server sends it to the owner and allies as a `radar` message, and the client draws fading blips (`RADAR_FADE_TICKS`) above the fog. Pulses are cleared in `commit()`.

## Single Player scenarios
- **Maps made for a scenario** (`MapDefinition.scenario`, `starts`, `foes`, `hordeFrom`; `mapStarts()` in `game/map.ts`): `starts` lists where the humans' bases go (a block of four bases 22 tiles apart; the `cluster()` helper), `foes` the bots' bases in Surrounded (default: the four corners) and `hordeFrom` the tile the horde appears at. Terrain for such a map is generated with `asymmetric` clear areas (not mirrored on all four corners). Horde: Last Redoubt, Siege Line, Dead End, High Ground, Long Night, Trench Works. Surrounded: Crossfire, Pincer, Bullseye, Ridgeback, Clearing, Rubble. `mapsFor(scenario)` lists them; the lobby filters the map list by game type.
- **Shared opposition in Co-op**: a co-op room with a scenario makes its horde or four bots once (`Match.shared`), when the first human joins; every human is on team 1 and faces them together. The horde (`HordeSpawner.addEnemy`) goes for the nearest building of any of them; the opposition is taken down with the last human. Capacity is the number of seats (4).
- A Single Player room (`mode=solo`) takes a `scenario` (`game/scenario.ts`; the URL and WebSocket parameter `scenario`): `standard`, `horde` or `surrounded`. A Co-op room (`mode=coop`) gets one only from its map: a map with `MapDefinition.scenario` sets it, and Free for all falls back to the default map. The Multiplayer form offers these as the game types Co-op Horde and Co-op Surrounded.
- **Surrounded**: `createMatch(seed, map, 'surrounded')` clears and fields a base at the map centre (`centreCorner`, a `Corner` with `offsetX/offsetY`), drops the shared centre field and the neutral wanderers, and the server gives the human that start and a `setUpAi` base in each of the four corners (attacks stretched by `SURROUNDED_BOT_PACE`). The human wins when all four are destroyed.
- **Horde**: no enemy base. `HordeSpawner` (`game/horde.ts`) puts a group at the opposite corner's clear patch every `HORDE_INTERVAL_TICKS`, sends it at the nearest enemy building, and grows the group and the class mix over time (`HORDE_*` in `rules.ts`). The horde is never "eliminated", so the only ending is the human's defeat. `Match` keeps a list of opponents per human (`bots`), so a human can face one bot, four, or the horde.

## Bots (the player-like AI)
- Single Player and co-op matches add bots (`game/ai.ts`, `AiPlayer`; `setUpAi` gives one the same starting base and classes a person gets). It plays by the same rules: it does not cheat (it is not in `Simulation.cheaters`), it mines, pays for everything from the common pool, and only sees what its own units and buildings see (plus the enemy start positions, which the lobby shows to everyone). `pace` stretches the time before its first attack (Surrounded uses `SURROUNDED_BOT_PACE`).
- It thinks once a second (`AI_THINK_TICKS`, staggered by owner id), in four steps: a census of what it owns, an update of what it has seen of the enemy (buildings are remembered until they die, units for 30 s), a build plan, then orders. About 0.03 ms a tick for four bots on average.
- **Plan** (priority order; at most `AI_MAX_SITES` plus builders/2 open sites, and a site only starts when the pool covers it; when something is wanted and unaffordable the bot saves instead of training army, except below a growing minimum army): a silo when the pool is nearly full, wind and solar generators and storage for what is running, a second field (an *expansion*: a chain of pylons from the base if needed, a silo, then two laser turrets), factories as harvesters grow, laser turrets between the base and the enemy (more over time or when attacked), flak turrets once it sees enemy missiles, a construction tower and charging pads. Sites go where there is a tile of space round them, clear of resource fields, and linked to the base's power network (so builders draw from the pool).
- **Units**: harvesters (more per field it holds), builders (up to 4), a Pathfinder that scouts the enemy start positions, then a weighted rotation of the combat classes (earlier ones first; the rotation only advances on a purchase, so an expensive pick is saved for rather than replaced by a cheap one). Heavy and super-heavy tiers are not built.
- **Army**: idle fighters gather at a rally point beside the own charging pad nearest the enemy and recharge there. A wave launches (attack-move to the least defended enemy building) once the gathered fighters outweigh the larger of a time-based threshold (`AI_ATTACK_BASE` plus `AI_ATTACK_GROWTH` per wave) and 1.2x the enemy army it has seen, and only with units that have the energy to reach the target; when the trip is longer than a charge allows it builds a forward outpost (pylons, a charging pad, a turret and two wind turbines) first. Enemy fighters near any own building pull the army back to defend; an attack that meets 1.8x its own cost is called off. Units that finish an attack carry on to the next target.
- Known limit: on the largest maps (Great Plains, Badlands, 150-tile marches) its armies run out of energy on the way and its attacks are slow or weak (see `TODO.md`).
- The old cheating bot (`game/bot.ts`, `setUpBot`) is still exported and its class list feeds the Horde.

## Programs: event blocks, one model, two views

Class behaviour is a **program of event blocks** (`flow/`), run by each unit's own CPU. Nothing runs, and nothing is paid, until an event the class has a block for arrives; an event with no block is dropped before it is queued.

```ts
let target = -1;

on(Detected, { watch: [ENEMY], range: 6, interval: 5 }, (kind, h) => {   // the sensor, configured on its block
  target = h;
  const hit = fire(h);        // actions are statements; queries may sit inside expressions
  if (hit === 0) {
    approach(h, 3);
  }
});

on(Idle, () => {              // fires when the CPU has nothing else to do
  config.rest(5);             // runtime settings live in the config namespace
});
```

- **One model, two views.** The **Flow IR** (`flow/ir.ts`: handlers with settings and parameters, statements, expressions) is the program. The TypeScript-subset **text** (`flow/text.ts`, parsed with Lezer) is its deterministic pretty-print, and the **node graph** (client) is another projection of it. `parseText` and `printText` round-trip exactly, so editing either view updates the other; statements keep their ids across text edits so graph layout survives. The stored form is the canonical JSON of the IR (`wst-flow`), plus editor-only `views` (node positions and the loose pieces of an unfinished graph) that the game never reads.
- **Events** (`flow/events.ts`): `Spawned`, `Idle`, `Every`, `Timer`, `Order`, `Arrived`, `Damaged`, `Detected`, `Visitor`, `Button`, `EnergyLow`, `EnergyFull`. Each block carries the **settings** of whatever raises it (sensor `watch`/`range`/`interval`/`sort`/`limit`, `Order` `types`, timer intervals, a button's label and key): constants only, filtered by the engine before an event is queued, so they cost nothing to run. Better sensors unlock more of the `Detected` options (`game/sensor.ts`).
- **Kinds of call** (`game/api.ts`): queries (inside expressions), actions (statements), and runtime settings (`config.rest(n)`, `config.laserPower`, `config.setModule`, `config.storageMode`). The compiler and the editors enforce the kinds.
- **Cost = nodes executed + wires followed** (`flow/cost.ts`), the same for text and graph: a statement costs 2, an operator or query on a wire 2, a variable read 2, an event parameter or call result 1, inline numbers and constants nothing, plus each call's own cost. A branch not taken costs nothing.
- **Running** (`flow/run.ts`): the program compiles (`flow/compile.ts`) to a flat instruction list. Each tick a unit's CPU gets its `cyclesPerTick`, runs queued events one at a time, and may **pause between statements** when the cycles are spent (a statement can overdraw the balance; the overdraft is repaid over the next ticks). Per-unit state is one `FlowState`; a unit with an empty queue, no timers and no `Idle` block is skipped with one check, so 1024 units tick in about 1-2 ms. A handler running over `COST.HANDLER_LIMIT` cycles crashes the unit's program (it reboots).
- **Lists and chains** (`flow/lists.ts`, 2026-10-29). A *list source* is a query flagged `list` that fills a shared 32-entry buffer with handles, nearest first (`findResources`, `findResourcesNear`, `findDepots`, `findChargers`, `findSites`, `findDamaged`, `findEnemies`, `findAllies` in `game/api.ts`). A **chain** is `source(...)` plus steps: `filter`, `map`, `sortBy`, `sortByDesc`, `take` give a list; `first`, `last`, `at`, `random`, `count`, `sum`, `min`, `max`, `minBy`, `maxBy`, `reduce` end it with one number. Functions are single-expression arrows (`r => dist(r) < 5`), compiled inline as loops over the buffer (no closures, no per-unit list memory: a chain runs inside one statement, and a handler only pauses between statements, so every unit shares the buffer). Chains cannot nest, and functions can call only queries. Costs: the source's cost, then per step `LIST_ELEMENT_COST` (2) per entry plus the function body (a sort adds one cycle per entry), and a list never exceeds `LIST_MAX` (32), so a chain is bounded and still under the handler limit. The IR has one new expression, `chain` (`fn`, `args`, `steps: {op, params, args}`); in text `const x = <any expression>` is read as `calc(x)` (a query that returns its argument), which the printer writes back as a plain const. Source builtins stay out of plain expressions: the checker asks for a chain ending. The graph shows a chain as one query node with its steps as text (edit them in the Text view).
- **Harvesting** (`HarvestLoop`, `DispatchHarvesters` in `flow/blocks.ts`) is written with chains: the home depot is the one minimising `dist(d) + 12 * crowdOver(d, crowdRadius, crowdLimit)` (harvesters beyond the limit near a depot count against it), then the field is the one among the `fieldsToChooseFrom` nearest that depot minimising `distBetween(depot, r) + 6 * crowd(r, 3)`. A field that cannot be reached is left out of the next choice; a full load waits for a depot with room.
- **Memory** (`flow/check.ts`): a program occupies one slot per variable, per distinct number written in it (other than -1, 0, 1) and per event parameter or `const` result of its biggest block, against the class's `memorySlots`. Settings do not count.
- **Events come from the simulation:** `Order` and `Button` from the command handlers, `Visitor` from `addVisitor`, `Arrived` from the movement system, `Damaged` from combat, timers, sensor sweeps and energy thresholds from `scriptSystem`.
- The old text-script VM no longer exists on this branch (it is on `main`). Saved design files from before it (`version` 1) have their old programs replaced by the current default of that name, or the new-class starter.

The `docs.html` pages generated from this metadata (events, call kinds, cost, memory, constants) are the language reference.
